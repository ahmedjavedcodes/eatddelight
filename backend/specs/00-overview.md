# Spec: Backend Foundation & Conventions

> Scope: the shared engineering contract for the Daughter's Delight backend — project structure, cross-cutting conventions, the Phase 1 scaffolding, and the Phase 10–11 hardening/release checklist. Feature behaviour (catalog, cart, orders, invoicing, admin) is specified in the per-plan specs `01`–`05`; this document is what all of them sit on.
>
> Source plan: `plans/backend/00-overview.md`. Architecture reference: `backend/CLAUDE.md`.

## Problem Statement

The backend is greenfield — `backend/` currently contains only `CLAUDE.md`. The build is split into five sequential slices (catalog / cart & favourites / orders / invoicing / admin), each with a detailed plan. Whoever picks up a plan (Ahmed, or anyone he hands it to) needs an already-agreed foundation to build inside: project layout, a single error envelope, money and time handling rules, migration discipline, a test harness, and lint/type gates.

Without that foundation each slice drifts — one endpoint returns `{"error": "..."}` and another `{"detail": "..."}`; money gets done in `float` and totals drift by a cent; `datetime.now()` is called inline and the "Monday special ordered on Monday" rule becomes untestable; someone hand-edits the schema and `alembic upgrade` from empty no longer reproduces production. That drift is exactly the rewrite churn the plan set exists to prevent, and it is hit on every plan and every PR. `CLAUDE.md` records the architecture but is not an executable, verifiable baseline. If this isn't pinned down first, the frontend gets an API it can't rely on and every feature re-litigates stack decisions.

## Functional Requirements

**Scaffolding (Phase 1)**

1. A runnable FastAPI service assembled by a `create_app()` factory in `app/main.py`, served by uvicorn, mounting all routes under `/api/v1`; `GET /api/v1/health` returns `{"status": "ok"}`.
2. A single `Settings(BaseSettings)` in `app/core/config.py` (pydantic-settings, `.env`-backed), exposed via an `@lru_cache`d `get_settings()` that is also a FastAPI dependency. `.env.example` is committed with placeholder values; real secrets (`SECRET_KEY`, `OWNER_PASSWORD`, DB password) are never committed.
3. An async DB layer in `app/db/`: `create_async_engine` + `async_sessionmaker`, and a `get_db()` dependency that yields an `AsyncSession`, commits on success and rolls back on exception.
4. `app/db/base.py` providing `Base` (`DeclarativeBase`), a `MetaData` with an `ix_/uq_/ck_/fk_/pk_` naming convention, and a `TimestampMixin` (`created_at`, `updated_at`) — all models use both.
5. A consistent error envelope `{"detail": <str|list>, "code": <stable_snake_case>}` for every handled error. `app/core/errors.py` defines a `DomainError` base (`status_code`, `code`, `detail`) plus subclasses; `create_app()` registers handlers for `DomainError`, `HTTPException`, and `RequestValidationError` that all emit that shape.
6. A `get_session_token` dependency in `app/api/v1/deps.py` that reads the `X-Session-Token` header, checks only that it is present and non-empty, and returns it as an opaque string — no signing, expiry, or server-side issuance.
7. Money rule: monetary columns are `Numeric(8, 2)` mapped to `Decimal`; `float` is never used for money. Order-line prices are snapshotted at order-creation time; cart-line prices are read live.
8. Time rule: `app/services/clock.py` exposes `now_pk()`, `today_pk()`, `earliest_requested_date()` in `Asia/Karachi`. Services never call `datetime.now()` / `date.today()` directly.
9. Layering rule: routers under `app/api/v1/` only parse input, resolve dependencies, call one service, and serialize; all business logic, transactions, price snapshotting and external-artifact building live in `app/services/`.
10. Async Alembic setup: `alembic/env.py` bound to `Base.metadata` and the app's `DATABASE_URL`; every schema change ships a hand-reviewed autogenerated revision; enum types are created explicitly in the migration.
11. A pytest harness: a disposable Postgres test database, per-test isolation via a SAVEPOINT rolled back on teardown, an `httpx.AsyncClient` + `ASGITransport` fixture with `get_db` overridden, and factory fixtures for `Category`, `Food`, `AddOn`, `AdminUser(owner)`, `AdminUser(staff)` plus an authed-client-per-role fixture.
12. Quality gates: `ruff check`, `ruff format --check`, `mypy app`, and `pytest` all green is the definition-of-done gate for each plan; `.pre-commit-config.yaml` runs ruff, mypy and pytest.
13. Local development runs against the **PostgreSQL 18 server already installed on the machine** (service `postgresql-x64-18`, superuser `postgres`), administered with pgAdmin or `psql`. Two databases — `eatddelight` and `eatddelight_test` — are created once (pgAdmin GUI or `psql`); connection details live only in `.env` (`DATABASE_URL` / `TEST_DATABASE_URL`). **No Docker / docker-compose.**
14. The Python environment is a project `.venv` (Python 3.13 via the `py` launcher); dependencies are declared in `pyproject.toml` and installed with `pip install -e ".[dev]"`. **Not `uv` or poetry** (uv is not installed on this machine); no lockfile.

**Process & decisions**

15. The build follows the dependency order `01 → 02 → {03 → 04, 05}`; a plan starts only once the previous plan's done-gate (FR12) is met.
16. Three client decisions are encoded as fixed behaviour (see Constraints): `PUT /admin/settings` is owner-only; custom orders carry four optional structured fields; the order-status set is `pending → confirmed → completed` (+ `cancelled`).
17. After plans 01–05 are green, the Phase 10–11 hardening/release checklist is executed as a final pass (CORS lock-down, rate limiting on public writes, structured logging, full error-shape coverage, OpenAPI cleanup, security headers, DB pool config, seed-typo review).

**Out of scope (deferred nice-to-haves, not dropped):** CI pipeline configuration; containerising the app itself; metrics/tracing beyond structured logs; load testing; an admin-JWT denylist/logout; email or SMS. Add only on explicit client request.

## Behaviour

This feature has no runtime end-user flow; its "user" is a developer picking up a plan, and its "states" are milestones of the backend build.

**Primary flow — implementing a plan**

1. **Set up.** Ensure the local PostgreSQL 18 service is running and the `eatddelight` database exists (create it once in pgAdmin or with `psql`). `py -m venv .venv` and activate it; `pip install -e ".[dev]"`; copy `.env.example` → `.env` and set `DATABASE_URL` to `postgresql+asyncpg://postgres:<password>@localhost:5432/eatddelight`; `alembic upgrade head`; `uvicorn app.main:app --reload`. Verify `GET /api/v1/health` → `200 {"status":"ok"}` and `/docs` renders.
2. **Pick the plan.** Take the lowest-numbered plan whose prerequisites (FR15) are satisfied — the first is `01`.
3. **Build inside the conventions.** New endpoints go under `app/api/v1/...` with an OpenAPI `tags=[...]`; new logic goes in `app/services/...`; new tables are models + a hand-reviewed Alembic revision; money is `Decimal`; "now" comes from `clock.py`; errors are `DomainError` subclasses; admin routers declare their accepted roles explicitly.
4. **Test.** Add tests to the plan's named files using the shared fixtures; run `ruff` + `mypy app` + `pytest`.
5. **Gate.** All green → the plan is done and unlocks the next.
6. **Harden.** After `01`–`05`: run the Phase 10–11 checklist, then the release checklist (full suite green; `alembic upgrade head` from empty reproduces the schema; `seed_menu.py` idempotent; flyer-typo keep/correct decision recorded with the client).

**Build states** (one-way, each transition gated by "that plan's tests + lint + types green"):

| State | Reached when |
|---|---|
| `scaffolded` | Plan 01 done — app runs, `test_health` green, no domain tables |
| `schema-ready` | Plan 02 done — all tables migrated, seed idempotent |
| `public-complete` | Plan 03 done — catalog / cart / favourites endpoints live |
| `checkout-complete` | Plan 04 done — orders + PDF invoice + WhatsApp handoff |
| `admin-complete` | Plan 05 done — admin auth, CRUD, contact form |
| `release-ready` | Phase 10–11 checklist complete |

## Constraints

**Stack (locked — no substitutions):** FastAPI (async); SQLAlchemy 2.x async + `asyncpg`; PostgreSQL 18 (local install); Pydantic v2 + `pydantic-settings`; Alembic (async template); pytest / pytest-asyncio / httpx `AsyncClient` + `ASGITransport`; ruff (lint + format); mypy (strict on `app/`, relaxed on `tests/`); admin auth via JWT access + refresh with `passlib[bcrypt]`; WeasyPrint for PDF (reportlab is an acceptable fallback if system deps are missing); **`venv` + `pip`** for env/deps (deps in `pyproject.toml`, `pip install -e ".[dev]"` — not `uv`/poetry); **locally-installed PostgreSQL 18** administered via pgAdmin / `psql` — no Docker.

**Product constraints (from `CLAUDE.md`):** no customer accounts / login; no online payment; single business (no multi-tenant); both menus require ≥ 1-day advance ordering in `Asia/Karachi`; full-menu items have min order quantity 3, daily specials 1.

**Resolved client decisions (this interview) — fixed behaviour:**

- **Settings editing is owner-only.** `PUT /api/v1/admin/settings` returns 403 for `staff`. Staff keep create/update on categories, foods and add-ons; all delete operations remain owner-only.
- **Custom orders carry optional structured fields.** `servings` (int), `budget_range` (str), `occasion` (str), `event_date` (date) — all nullable. `custom_description` stays the only required field when `order_source = custom_request`. When `event_date` is supplied it is subject to the same "≥ tomorrow, Asia/Karachi" rule as `requested_date`. **This revises plan 02 (new `Order` columns) and plan 04 (`OrderCreate` schema + validation).**
- **Order status set is `pending → confirmed → completed`**, plus `cancelled` reachable from any non-terminal state (`pending`, `confirmed`). Transitions are forward-only. **This revises plan 02 (`OrderStatus` enum) and plan 05 (`ALLOWED_TRANSITIONS`).**

**Non-negotiable engineering rules:** the `{"detail","code"}` error envelope on every path; `Decimal` money; `clock.py` for every "now"; every schema change via a hand-reviewed migration; the per-plan green gate before the next plan.

**Explicitly deferred / off the table for now:** app containerisation, CI config, metrics/tracing, JWT denylist, email/SMS. No timeline or budget constraints were supplied.

## Edge Cases and Error Handling

| Trigger | Expected Response |
|---|---|
| A required env var (`SECRET_KEY`, `DATABASE_URL`, `OWNER_EMAIL`/`OWNER_PASSWORD`) is missing from `.env` | App fails fast at startup with a Pydantic `ValidationError` naming the missing field; it never boots with a default value for a secret. |
| A handler raises a `DomainError` subclass | Registered handler returns the subclass's `status_code` with body `{"detail": <message>, "code": <stable_snake>}`; no stack trace. |
| A request body / query fails Pydantic validation | `RequestValidationError` handler returns 422 `{"detail": <errors>, "code": "validation_error"}`. |
| An unhandled 404 / 405 / 500 occurs | Reshaped to the same `{"detail","code"}` envelope (hardening item); no framework HTML or traceback in the response body. |
| `X-Session-Token` header absent on a cart / favourites / order request | 422 via the standard missing-required-header path; the message identifies the header. |
| Money is computed or typed as `float` anywhere in `app/` | Treated as a defect in review; order totals must reconcile exactly to line-price snapshots. |
| A service calls `datetime.now()` / `date.today()` directly | Defect — must route through `clock.py` so tests can freeze time (the Monday-ordered-on-Monday case is otherwise untestable). |
| Schema changed without an Alembic revision | Defect — `alembic upgrade head` from an empty DB must reproduce the live schema. |
| An autogenerated migration is committed unreviewed | Not allowed — autogenerate misses enum value changes, renames, `server_default` and check constraints; every revision is hand-reviewed. |
| A test leaks rows into another test | Indicates a fixture opening its own connection/commit outside the SAVEPOINT; fix the fixture — isolation is per-test rollback. |
| Concurrent writes needing ordering/uniqueness (e.g. invoice numbers) | Foundation supplies the transactional `get_db` and naming-conventioned unique constraints as the backstop; the retry logic is defined in the owning feature spec (04). |
| `custom_description` omitted on an `order_source = custom_request` order | 422 `{"code": "custom_description_required"}`. Empty structured fields (`servings`, `budget_range`, `occasion`, `event_date`) are allowed. |
| `event_date` on a custom order is today or earlier in `Asia/Karachi` | 422 `{"code": "advance_order_required"}` — same rule and code as `requested_date`. |
| An admin router is added without an explicit `require_role(...)` declaration | Defect — there is no implicit "any admin" default; every admin route names its roles. |
| An order-status transition goes backward, or leaves `completed` / `cancelled` | 409 `{"code": "invalid_status_transition"}`. |
| Release attempted before the Phase 10–11 checklist is complete | Release blocked — CORS lock-down, public-write rate limits, error-shape coverage, `response_model`s and security headers are release gates. |
| `seed_menu.py` is run more than once | Idempotent — no duplicate rows, prices reset to seed values, the owner password is never rotated. |
| Flyer typos (`Khauasay`, `Ceasar`, `Sizler`, `Raps`, `Alo`) reach production unreviewed | Release checklist requires an explicit keep-verbatim-or-correct decision with the client; `slug` values stay stable regardless of the decision. |

## Acceptance Criteria

**Scaffolding**

- [ ] Given a clean checkout, the local PostgreSQL 18 service running, the `eatddelight` database created, the `.venv` set up with `pip install -e ".[dev]"`, and `.env` copied from `.env.example` with `DATABASE_URL` pointed at the local server, when `alembic upgrade head && uvicorn app.main:app` runs, then `GET /api/v1/health` returns `200 {"status":"ok"}` and `/docs` renders.
- [ ] Given `SECRET_KEY` removed from `.env`, when the app starts, then it exits with a Pydantic `ValidationError` naming `secret_key` and serves no traffic.
- [ ] `get_settings()` returns the same instance on repeated calls and is usable as a dependency.
- [ ] `get_db()` commits after a successful request and rolls back when the handler raises.
- [ ] Every model inherits `Base` and `TimestampMixin`; generated DDL uses the `ix_/uq_/ck_/fk_/pk_` naming convention.
- [ ] `tests/test_health.py` passes against the disposable test DB via `AsyncClient` + `ASGITransport`.

**Conventions**

- [ ] Given a handler that raises a `DomainError` subclass with `status_code=409, code="item_unavailable"`, when it is called, then the response is `409 {"detail":"…","code":"item_unavailable"}` with no traceback.
- [ ] Given an invalid request body, when posted, then `422 {"detail":[…],"code":"validation_error"}`.
- [ ] `clock.now_pk()` returns an `Asia/Karachi`-aware datetime; monkeypatching it in a test shifts `earliest_requested_date()` accordingly.
- [ ] A search of `app/services/` finds no direct `datetime.now(` / `date.today(` calls.
- [ ] No value in `app/` is typed or constructed as `float` for money; all monetary values are `Decimal` / `Numeric(8,2)`.
- [ ] `get_session_token` raises the standard 422 when `X-Session-Token` is missing and returns the raw string otherwise.

**Migrations & build order**

- [ ] `alembic upgrade head` from an empty database reproduces the full schema; `alembic downgrade base` tears it down cleanly, including enum types.
- [ ] Each plan's named test files plus `ruff check` + `ruff format --check` + `mypy app` pass before the next plan begins.
- [ ] `.pre-commit-config.yaml` runs ruff, mypy and pytest.

**Resolved decisions**

- [ ] The `OrderStatus` enum is exactly `pending, confirmed, completed, cancelled`; `ALLOWED_TRANSITIONS` permits only forward moves plus `→ cancelled` from `pending`/`confirmed`; any backward or from-terminal transition returns `409 invalid_status_transition`.
- [ ] `Order` has nullable `servings` (int), `budget_range` (str), `occasion` (str), `event_date` (date); a `custom_request` with only `custom_description` succeeds (201), and one without `custom_description` fails `422 custom_description_required`.
- [ ] Given an authenticated `staff` user, when they call `PUT /api/v1/admin/settings`, then `403 forbidden`; the same call as `owner` succeeds.
- [ ] Given a custom order whose `event_date` is today in `Asia/Karachi`, when it is submitted, then `422 advance_order_required`.

**Hardening / release**

- [ ] After plans 01–05: CORS is restricted to the real frontend origin(s); `POST /cart`, `/cart/items/*`, `/orders`, `/favourites`, `/contact` are rate-limited from `RATE_LIMIT_PUBLIC_WRITE`.
- [ ] Every route declares a `response_model`; every router has `tags`; every request body carries at least one example.
- [ ] 404 / 405 / 500 responses use the `{"detail","code"}` envelope; no response contains a stack trace.
- [ ] Security-headers middleware sets `X-Content-Type-Options`, `Referrer-Policy` and a docs `Content-Security-Policy`.
- [ ] `seed_menu.py` run twice leaves row counts unchanged; the flyer-typo keep/correct decision is recorded with the client and `slug` values are unchanged afterward.
